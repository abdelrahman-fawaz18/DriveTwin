# ADR 0050. Seal one speed-cap decision and verify authority at the bus

Three independent requesters can propose different caps for the same simulated bus. For example, the energy service can ask for 5 m/s, the thermal service for 3 m/s, and the operator for 4 m/s. Arbitration chooses among eligible proposals. Local protection can still veto the winning proposal at the bus.

Enable arbitration explicitly for a fresh registered run and bus through the optional Compose overlay. The opt-in is saved for that run and bus. The three requesters use separate credentials and fixed issuer identities. Each can submit one immutable proposal. A byte-identical retry returns the original ID. The service derives precedence from the authenticated role, and the request format has no priority field. A scoped operator explicitly seals the batch. At the fixed handoff step of 4 simulated seconds, the service evaluates the original validity windows and ranks eligible proposals operator, thermal, then energy. An expired operator proposal leaves the thermal proposal eligible. A batch with no eligible proposal produces no dispatch. A sealed batch admits no new proposal or replacement.

Migration 004 adds the opt-in, proposal, and decision tables. The database transaction saves one decision and the corresponding command together. Concurrent seal requests return the same decision. The decision records the original proposer and the assessment of each submitted proposal. The existing command journal receives a command under the distinct dispatch coordinator identity, with the winning proposal's ID, parameters, timing, and original elapsed-time deadline. Direct operator command submission is disabled for the opted-in target. Existing targets use the ordinary path.

The database assigns the decision a generation number, called a fencing token. The trusted simulator announces support for `evdt-fence/1` before receiving a handoff. It first checks its own speed ceiling. Immediately before actuation it asks the authenticated command service to confirm the generation, command, run, bus, and active reservation, then verifies the original clock lease. A stale token or a request to raise the local ceiling causes a durable refusal without actuation. A refused or acknowledged reservation stays closed. An independent observer verifies the speed change on successful runs.

The profile covers one sealed decision per simulated run and bus with one trusted executor. The stale-token test injects an older number into the real verification path. Distributed takeover, a second authority generation on the same active bus, active plant restart, and backup recovery of authority records require separate qualification.
