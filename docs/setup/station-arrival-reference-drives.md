# Collect and qualify station-arrival reference drives

A reference drive is a measured run of the simulated bus. It gives us an independent result to compare with a forecast. For example, a prediction can say the bus will reach a charger with 36 kWh, while the simulated battery might reach a low of 34 kWh before recovering some energy during braking. The route violates the 35-kWh reserve even if the arrival reading is above it. For each drive, keep both the energy at the stop and the lowest energy along the approach and declared wait. [Charging policy](../charging-policy.md)

## What the collector measures

SUMO, our traffic simulator, owns the bus's motion and battery state. The collector reuses the reviewed road network, the bus and energy parameters, and the existing energy balance check. It uses TraCI, SUMO's local control and measurement interface, to advance one 0.2-second step at a time and read the actual lane, position, speed, and battery state. The bus follows a directed path to a scheduled stop in the catalog. A valid arrival requires both the stop flag and zero measured speed. The first run showed that the flag can appear while the bus is completing its final braking step. The full bus must fit inside the configured lane interval, allowing 0.1 m for the simulated stop position. [SUMO vehicle measurements](https://eclipse.dev/sumo/docs/TraCI/Vehicle_Value_Retrieval.html) · [Station catalog](../../simulation/montreal/charging-stations-1.0.0.json)

The first inserted, stationary battery reading is time zero. Each following reading must reconcile with the energy used or regenerated during that step. Charging is absent from the simulation configuration and the collector checks that each step reports zero charge received. Regenerative braking can still return energy to the battery. The run stops after the specified wait and checks that the energy drawn while stationary matches the configured equipment load. Collision, relocation, missing vehicle, depletion, an invalid stop, or reaching the time limit fails the run. A measured reserve violation is retained as a valid outcome if the bus stays above zero and the drive completes. [SUMO battery model](https://eclipse.dev/sumo/docs/Models/Electric.html)

## Development and reserved cases

The [versioned drive design](../../qualification/charging/station-arrival-design-1.0.0.json) records six development drives and six reserved drives. Each set contains two drives per station. The development set includes nominal charge and near-reserve approaches, with a no-charge wait where the station allows a queue. The reserved set uses different departure edges for the same station, separate seeds, and distinct charge, auxiliary-load and wait settings. The collector checks the routes of all twelve cases on the static network. It only runs the development cases.

The evaluation domain starts with one 18,000-kg simulated bus, 350 kWh usable capacity, starting charge from 10.1% to 16%, auxiliary demand from 8 to 12 kW, and waits from 0 to 45 simulated seconds. The vehicle begins at rest on the reviewed network. The design includes its traffic lights and road limits and assumes no other vehicles. Those ranges describe the intended domain. The finite cases provide evidence at their sampled points. Moving starts, other capacities or routes, real traffic, charger faults and physical vehicles need separate evidence.

## Qualification protocol

1. **Separate inputs from outcomes.** The prediction receives the admitted departure state, including observed energy or charge, motion and location, auxiliary demand, and their timestamps and quality. It can use the declared capacity, pre-drive directed route, station profile, and expected wait. The isolated evaluator keeps the later motion, actual battery trace, stop time, and realized wait. Use a versioned list of inputs and record their source and simulated decision time. Future live integration must verify authentication, freshness, and observation quality separately from this offline fixture.
2. **Develop and freeze the comparison.** Compare the candidate with a simple distance-and-auxiliary-energy estimate using the same allowed inputs. Use the development outcomes to check calibration and set explicit limits for arrival-energy error, charge error, underprediction of consumption, interval width and coverage, and decision availability. Derive the error budget from the reserve and near-reserve decisions. Keep the existing Phase 2 accuracy limits tied to their original known-route experiment. Before any reserved collection or scoring, record the chosen model, policy, thresholds, input contract, case list and fingerprints in an immutable evaluation manifest.
3. **Evaluate once on reserved outcomes.** Use a separate guarded run to seal each prediction before revealing its outcome to the scorer. Score arrival error in kWh and charge percentage points, worst optimistic error, interval coverage and width, and reserve classification. Test the reserve using the measured minimum through the wait. A false feasible result occurs if the advisor passes a station whose measured minimum is below reserve. Require zero false feasible results in the claimed evaluation cases. Report false exclusions and require the frozen availability criterion and positive feasible cases so rejecting everything cannot qualify the model. Preserve all six case results, including failures or unavailable predictions. Small-sample coverage is a count, not a probability guarantee.

## Reproduce the six development drives

1. Open PowerShell in `<checkout>`. The launcher uses the existing Ubuntu Docker Engine and simulator image. This runs one isolated container without external network access. The project is mounted read-only and only the private evidence directory is writable. Use a new output name each time. [Launcher guide](linux-launcher.md)

   ```powershell
   New-Item -ItemType Directory -Path evidence/p4 -Force | Out-Null
   python scripts/linux.py --timeout 180 -- docker run --rm --network none --read-only --memory 512m --tmpfs /tmp:size=128m,mode=1777 --mount type=bind,source=<checkout>,target=/workspace,readonly --mount type=bind,source=<checkout>/evidence/p4,target=/output -w /workspace -e PYTHONPATH=/workspace/src evdt-energy-collector:p2 /app/.venv/bin/python -m scripts.charging.collect_station_arrivals --output /output/my-station-arrivals
   ```

2. Expect one `Collected ...` line per development drive. The local TraCI client can print connection retries while SUMO starts. Success requires exit code 0, six drive records, `passed: true`, and `reserved_collected: false` in `evidence/p4/my-station-arrivals/qualification.json`. Each drive folder contains its route, log, and a JSON Lines trace, which stores one reading per line.
3. Compare arrival energy, minimum energy, and energy after the wait. A `reserve_maintained: false` row indicates the measured minimum fell below 35 kWh. Preserve that result for the model evaluation. A failing run preserves its partial records and failure message. The container is removed when the command exits.
