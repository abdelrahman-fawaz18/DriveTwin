# Integrated release qualification baseline

An integrated test runs the ordinary parts together. For example, a simulated bus sends a reading through its durable queue, the broker delivers it, the database saves it, and the dashboard displays it. Phase 6 checks that complete chain under sustained use and failures. The **baseline** fixes the inputs, test order, and rules before measuring. ## First monitoring configuration

Use Windows PowerShell and the existing launcher to run Ubuntu's Docker Engine. **Docker Compose** reads a list of related services and starts them together. Use `ops/compose/compose.monitoring.yaml`, then `ops/compose/compose.extension.yaml`, with a temporary override for the exact run and asset list. An override supplies run-specific settings without editing the underlying service definition.

Use the normal per-asset SQLite queue, authenticated broker, ingestion, PostgreSQL database, read API, and the single-page fleet view in pinned automated Chromium. Use the Montreal sustained simulation, telemetry schema 3.2.0, fleet catalog 1.4.0, and source recipe version 2.2. A **schema** defines the accepted message shape. The **catalog** defines the signals and units. The **recipe** binds the registered source and asset to declared inputs and timing. The fixture uses bus-001 alone or bus-001 through bus-010 as specified. Each asset has its own write identity. The dashboard reads by permission, and replay has separate credentials and provenance. The monitoring workloads run with command authority, optional bounded storage, and automatic retention off.

Record the exact built image identities, final configuration and source fingerprints, tool versions, migrations, generated bindings, and owned resources before a timed run. A fingerprint is a compact identifier for file bytes. The baseline pins committed reference inputs and the source revision. P6-A2 must review changed paths and bind the eventual test artifacts. ## Test order and clocks

Warm up for 60 wall-clock seconds before each declared measured interval. Count warmup separately. Use a common start barrier to wait for services, the browser, and every participating source to be ready. A **monotonic clock** measures elapsed computer time without jumping when the calendar clock changes. Simulation time describes the bus scenario. Simulated seconds cannot substitute for measured wall-clock seconds.

| Checkpoint | Test | Measured interval and expected work |
|---|---|---|
| P6-A2 | Monitoring harness and one-bus smoke test | 30 seconds after warmup, 30 events and 600 readings. A smoke test is a short proof that the parts start, connect, and report evidence. It has its own label. |
| P6-B1 | Fault-free W0-30 and W1-30 | One bus, then ten buses. Each runs for 1,800 measured seconds at 1 event per bus per second. Expect 1,800 and 18,000 measured events respectively. W1-30 supplies the full W1 display-latency and host-capacity measurement. |
| P6-B2 | W3 burst | Ten buses at 1 event per second for 60 seconds, 5 for 60 seconds, then 1 for 120 seconds. Expect 4,800 events. A burst tests a temporary spike in arrivals. |
| P6-B2 | W4 recovery | Ten buses at nominal rates for 3,600 seconds. Broker unavailable from measured t=600 to t=900. Restore the broker and restart ingestion at t=900. Start the 120-second drain clock only once both are ready. Keep the sources and display active and reconcile all 36,000 events, including 3,000 generated during the outage. |
| P6-B2 | W1 queue-capacity outage | Separate 1,800-second broker outage at nominal fleet rate. Verify 18,000 original events and per-asset physical storage with admitted envelopes covering the declared 8,192-byte boundary. Hold the capacity claim if that boundary cannot be exercised through the normal path. |
| P6-B3 | W2 soak | Ten buses at nominal rate for 7,200 measured seconds. A soak checks whether resources or backlogs grow over time. Reconcile all 72,000 events and 1,440,000 readings. Keep the fleet view subscribed, check freshness at declared intervals, and measure resources throughout. |

Run each workload separately. The W0/W1 short results retain their original durations. The two-hour history dataset was produced separately and remains usable for history testing. [Frozen workloads and exact rules](../workloads-and-metrics.md)

## Which evidence can carry forward

**Reuse** means a previous measurement supports the same claim under compatible code, inputs, and conditions. If a path that could affect the outcome changed, keep the previous outcome and rerun the affected behavior. Reuse the original history dataset itself after validating its manifest and exact required image. Retest the current reader or restore behavior as indicated below. The original application-image guard still applies to the original restore.

## Fault and compatibility checks beyond fleet monitoring

Use a separate one-bus command fixture after monitoring qualification. Keep one service responsible for granting actuation. First show the healthy cases and authorized effects. Then inject cooling degradation, reserve a charging action, and make the thermal or freshness gate refuse it before grant. Withdraw station power during the transport interruption. On recovery, reconcile the originals and refuse the stale handoff. An independently observed safe effect can follow only a fresh eligible request. This is a planned integrated scenario. Its adapter and exact timing must be qualified before execution. Any expansion of the single parked-bus automatic charging scope requires its own authorization. [Existing charging boundary](../adr/0063-qualify-bounded-automatic-charging.md) · [Offline thermal boundary](../adr/0067-bounded-thermal-intervention.md)

Qualify startup, backup, restoration, retention preview before deletion in owned storage, comprehensive browser visuals and deployment/reboot cases separately. ## Host readiness and stopping rules

The Windows precheck samples available physical RAM, commit headroom, and the Ubuntu working set about once a second while a lightweight Ubuntu process is active. **Commit headroom** is how much memory Windows can still promise to back with RAM or paging files. It measures a different constraint from available physical RAM. Check at least 30 seconds of valid coverage, at least 2 GiB available RAM and 1 GiB commit headroom at each sample, and positive Ubuntu working-set coverage. Keep at least 20 GiB free on the limiting disk after projected growth. Use one owned attempt at a time.

During a run, apply the full Q-12 thresholds. Keep the existing operational emergency guard for under 512 MiB of available RAM or under 1 GiB of commit headroom for 10 seconds. Stop on required measurement gaps, unsafe or unauthorized control, unexplained loss, input mismatch, or a resource guard failure. Preserve partial data as incomplete and clean up only the run's own containers and volumes. Review the evidence before choosing any retry. A Linux **cgroup** measures a group of processes, so a container's memory can be tracked separately from the whole Ubuntu environment.

The A1 sample had **1.11 GiB** minimum Windows available memory and a **34.5-second conservative upper bound** below 2 GiB, with no test containers active. The emergency guard passed. The full launch precheck failed. Ubuntu Docker and disk space were available. The P6-A2 precheck improved to **1.41 GiB** and still held the live test. A larger Ubuntu memory allocation cannot create Windows physical memory. Before any live run, take a fresh precheck in the intended operating conditions.
